# mwj-design-system 支持项目自己的 DESIGN.md（2026-11-12）

> 状态：**已完成**（2026-11-12）；各项目副本的分发未做，待另行确认。

## 一、背景

调研 [VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md)（84 份按 Google Stitch `DESIGN.md` 格式写的品牌官网设计分析）后的结论：

- 内容不对口：那些文件分析的是营销页，MWJ 管的是后台类页面，且 MWJ 已有自己的 Token，不引入整库。
- 格式可借鉴：一份放在项目里的 `DESIGN.md`（文件头 YAML token + 正文规则），正好补上 `mwj-design-system` 的一个缺口。

缺口：v2.0 规定"项目有自己的风格时以项目现有风格为准"，但没规定这个风格写在哪，每次只能靠 grep 代码推断；代码里推断不出的规则（例如"危险操作不用实底"）会丢。

## 二、改动范围

| # | 文件 | 改动 |
|---|---|---|
| 1 | `skills/mwj-design-system/SKILL.md` | 「适用范围」第 1 步改为先找项目的 `DESIGN.md`，有则以它为准；没有再走原来的 grep 判断。新增「项目自己的 DESIGN.md」一节（何时建议沉淀、写入规则）。description 补触发条件 |
| 2 | `skills/mwj-design-system/references/design-md-template.md` | 新增精简模板 |
| 3 | `README.md`、`CLAUDE.md`、`docs/changelog.md` | 按文档规范同步 |

不做：不把 awesome-design-md 的文件收进仓库；不改 MWJ Token；不改版本号；不动各项目副本（分发另行确认）。

## 三、设计取舍

- **查找位置**：项目根，其次 `docs/`、`doc/`（与 `MWJ_Design_System.md` 的惯例一致）。
- **有 `DESIGN.md` 且描述独立风格**：颜色、字体、圆角、阴影、间距、组件样式全部以它为准；本规范只借用与风格无关的部分。它没写到的看现有同类组件，定不下来问用户，不拿 MWJ Token 补。
- **有 `DESIGN.md` 且声明采用 MWJ**：本规范照常适用，变体按它写的。
- **独立风格但没有 `DESIGN.md`**：行为同 v2.0（以现有风格为准），交付时建议沉淀一份；写入前须用户同意。
- **模板**：只保留本人项目用得上的章节，写代码里已生效的值，token 名与代码变量名一致。

## 五、测试方法

临时夹具项目（暖纸色独立风格的 Vue 小项目，放会话临时目录，不进仓库），`docs/DESIGN.md` 里有一条只读它才知道的规则（危险操作用描边按钮，不用红色实底），而 `tokens.css` 里有 `--danger` 色值，不读 `DESIGN.md` 的做法会做成红色实底。让子代理按 skill 新增一个删除确认弹窗，检查：

1. 是否读了 `docs/DESIGN.md`；
2. 危险按钮是否为描边；
3. 是否混入 MWJ Token（`#1677FF`、`Mwj*`）；
4. 无 `DESIGN.md` 场景：是否不擅自写入、是否在交付时建议沉淀。

## 六、测试结果

每个场景各跑 1 次（子代理按 skill 在夹具项目里新增删除确认弹窗，产出文件由主会话逐个核对）。

| 场景 | skill 版本 | 读了 `DESIGN.md` | 危险按钮 | 混入 MWJ Token | 擅自写其他文件 |
|---|---|---|---|---|---|
| 有 `docs/DESIGN.md` | 改动前（基线） | 是 | 描边 | 否 | 否 |
| 有 `docs/DESIGN.md` | 改动后 | 是（先跑 `ls` 探测） | 描边 | 否 | 否 |
| 无 `DESIGN.md` | 改动后 | — | **红色实底** | 否 | 否，交付时建议沉淀 |
| 无 `DESIGN.md`（措辞修正后复验） | 改动后 | — | 红色实底 | 否 | 否，交付时建议沉淀 |
| 用户要求沉淀 `DESIGN.md` | 改动后 | — | — | 否 | 否，按模板写在项目根 |

结论：

- 基线已经会自己找到并遵守 `DESIGN.md`，所以"有则以它为准"这条规则本身增量小，写得很短；增量在模板、"没有时建议沉淀"和冲突处理规则。
- 有无 `DESIGN.md` 的差别落在代码里看不出来的规则上：有的两次都是描边危险按钮，没有的两次都做成红色实底。
- 第一轮无 `DESIGN.md` 场景指出两处措辞不清（冲突处理规则只写在"有 `DESIGN.md`"分支下；"交付时提一句"的对象不明），已改为两个分支共用的「项目用自己的风格时」并复验，复验中不再出现这两处疑问。
- 沉淀场景指出模板四处说明不足（无 token 的字号怎么写、代码里没有的键怎么填、`components` 能否加属性、"代码看不出来的规则"与"不要编"的张力），已在模板里补齐；补齐后的模板未再复跑。
- 基线过程中发现探测风格的 grep 命令在 zsh 下报 `no matches found`，已修复并记入 `docs/bug-fixes.md`。

局限：每个场景只跑了 1 次，夹具只有一个；测试里是直接指定代理读 skill，没有覆盖"独立风格项目里 skill 是否会被自动触发"。
