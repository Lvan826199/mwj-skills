# 回执审批清单（Linux 侧）

## 1. 新鲜度（任一不符 → 结论「不可测」，停止判定）

- [ ] 回执日期是本轮（`date` 看今天几号；`git log -1 --format=%ci -- <回执文件>` 看提交时间）
- [ ] 被测 commit ≥ 本轮推送的 hash（`git merge-base --is-ancestor <本轮hash> <回执hash>`）；任务单没写 hash 时，以下发任务单的那次提交为基线（`git log -1 --format=%h -- <当前任务.md>`）
- [ ] 多仓库联调：每个仓库的 commit 都核对
- [ ] 产物 LastWriteTime 晚于拉取时间；版本号 / versionName / build-stamp 等于本轮
- [ ] 产物 SHA256 或大小**与上一轮回执完全相同 → 旧包**（MoneyFree R4 第 15 次就是这样被打回的）
- [ ] 任务单要求跑测试时：pytest 通过数与本地一致（不一致要解释差在哪）

## 2. 逐项判定

- [ ] 每个任务单编号都有对应结果，缺项算 ⏭ 并追问
- [ ] 判据看设备侧独立证据；只有被测系统自己说「成功」的不算通过
- [ ] 数字和日志原文对得上，不信回执里的形容词
- [ ] **人工原话和日志互证**：人说「正常」，日志里也要有这次操作的新记录；没有就要求重做（MSCA 回执 55 第 5 项就是这样做的）
- [ ] 「偏离」一节里的环境改动是否影响结论
- [ ] 「疑问」一节逐条回应

## 2.5 发布类轮次另核

- [ ] 每个对外动作（合并、打 tag、发 Release）都有用户确认原话
- [ ] tag 指向预期的提交（模型 B 应指向 master 上的合并提交）
- [ ] Release 附件的 digest 等于回执里的 SHA256
- [ ] 各发布渠道的边界符合项目规则（哪个渠道上传哪些产物）

## 3. 结论与引用

- 汇报：结论先行（通过 / 部分通过 / 阻塞 / 不可测）→ 失败项 → 原因判断（标明证据等级：已确认 / 高度可能 / 未证实）→ 下一步
- 引用回执写成「回执 <编号>（<日期>，<hash>）第 N 项显示…」
- 回执结论和用户真机体验对不上 → 先问用户的使用场景，不要强行用回执去说服用户

## 4. 收尾

- [ ] 审批写回同一文件并推送（仓库协议模式）
- [ ] 失败项 → 修复 → 复验提示词（只含未过项 + 波及项）
- [ ] 问题跨多轮且本轮确认解决 → 调用 `postmortem` skill
- [ ] 新证实的设备约束 → 补进行为回放测试或归因文档
- [ ] 当前任务单归档到 `历史任务/`
