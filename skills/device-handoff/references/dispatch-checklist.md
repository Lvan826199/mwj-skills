# 下发前自检清单（Linux 侧）

来源：MSCA `doc/联调/README.md` 的 17 条自检（多次真机轮次白费后总结），加上历史会话里用户的纠正。每轮下发前逐条过，不过不发。

## 一、这一轮该不该发、发什么

- [ ] **一轮只解决一个问题**：「验证修复」和「回答问题」二选一，不混入顺手的重构、调参。
- [ ] **对面能拿到新代码**：commit 已推送，hash 写进第 0 步；动了后端或打包链路就不能写「不用重新打包」。
- [ ] **探针/验修复轮次用开发模式**（源码直跑），只有改了打包链路或发版前验收才打包。
- [ ] **不重复已验证项**：上轮回执已通过、且本轮改动不影响的项，不再跑。
- [ ] **不凭空加前置条件**（设备台数、额外环境）；真有下限就写原因，或改代码把下限降下来。

## 二、本地先挡住的回归（假服务盖不住的三层）

- [ ] **路由**：动了默认值、参数、分支条件 → 回答「不带参数的那条命令现在走哪」，并有一条端到端测试钉住。
- [ ] **预算**：超时、重试、阈值常量的注释写清出处（哪份回执第几项的实测值），有测试断言不低于实测最慢值。
- [ ] **连接寿命**：设备约束（一条连接只受一次请求等）进了行为回放测试；测试走真实入口 `cli.main(argv)`，而不只是被测函数。
- [ ] **提示语改在最终拼出来的地方**：有测试断言用户最终看到的 message 里有这句话。
- [ ] **界面改动有真渲染测试**，并且自己用无头浏览器截图看过，确认没问题才发给人。
- [ ] **同一功能有两条调用路径，两条都验**；不拿 A 路的结论替 B 路背书。

## 三、判据写得对不对

- [ ] **写进通过标准的每个字符串、数字都回代码核对过**：日志真会打出来、条件真会成立。
- [ ] **判据看设备侧独立证据**，不拿被测系统自己的返回当证据（装没装上看设备侧时间戳，不只看接口 `success`）。
- [ ] **意料之外的异常，第一句就要完整栈**，不凭推理猜位置。
- [ ] **健康指标有最大值**：给出平均值的地方，同窗的最大值也要列出；明显异常要升到 WARNING 级别；判据点名要看哪一行指标，不能只写「搜不到 ERROR」。
- [ ] **循环里每一段都有探针**：有一段没量到，就不能说整条链路是稳的。

## 四、执行者分工

- [ ] agent 只做命令行；不点界面、不截图、不抢焦点。
- [ ] 人只看人才能判断的（好不好用、看不看得清），清单短、能照着点。
- [ ] 不问人日志里已有的东西——让 agent 去取。
- [ ] 会打断人的动作（装包、重启、拔插）写明「先问一句」。

## 五、文本本身

- [ ] 提示词整段可复制，不需要用户再拼接或手动打开文件复制。
- [ ] 路径用正斜杠；不含任何凭据。
- [ ] 写清预计耗时、失败时的重试上限和停止条件。
