# Device Handoff：跨机器真机联调

两台机器只通过 **git（或共享盘）+ 固定格式文档** 交换信息，不靠人肉复制日志。
人只做两件事：转发一句话、看界面（agent 验不了的）。

## 第 0 步：判断角色

| 信号 | 角色 |
|---|---|
| 当前平台是 Windows；用户说「按联调任务执行」「跑一下当前任务」「写回执」 | **执行侧** → 只看 §执行侧 |
| 当前平台是 Linux/macOS；用户说「给提示词」「发任务单」「回执来了」「审批」「复验」，或粘贴来一段回报 | **下发侧** → 看 §下发侧 |

拿不准就用 AskUserQuestion 问一次，不要两边的事都做。

## 第 1 步：读项目自己的协议（两个角色都要做）

协议以仓库为准，skill 只是兜底。按顺序查找，找到就**照项目的来**：

```bash
ls doc*/联调/README.md doc*/回执/模板.md 2>/dev/null; ls -d doc*/联调/回执 doc*/回执 2>/dev/null
grep -nE "跨机器|联调|回执|Windows 侧|真机" AGENTS.md CLAUDE.md docs/打包发布.md 2>/dev/null | head -40
```

- 有协议（如 MSCA `doc/联调/`、MoneyFree `docs/回执/`、iPhoneUsbTouch `docs/打包发布.md §7` + `docs/联调/回执/`）：沿用它的目录、文件命名、commit message、回执骨架。只有回执目录、没有 README 的，也算有协议：先读最近两份回执，照它们的格式来。
- 没有协议：下发侧用 AskUserQuestion 让用户选交换方式——
  1. **仓库协议（推荐）**：按 `references/protocol-readme-template.md` 建 `docs/联调/`，以后 Windows 侧只需一句「按联调任务执行」；
  2. **对话粘贴**：提示词整段给用户转发，回执由用户粘回来；
  3. **共享盘**：回执写到共享盘目录（路径与凭据从本机配置读取，**绝不写进提示词或仓库**）。

## 下发侧（Linux）

### A. 下发前自检（每轮必做，不过不发）

逐条过 `references/dispatch-checklist.md`。最常犯的五条：

1. **一轮只解决一个问题**：要么「验证这个修复」，要么「回答这个问题」，不混重构和调参。
2. **新代码先让对面拿到**：改了后端/打包链路就不能写「不用重新打包」；commit 已推送、hash 写进任务单。
3. **判据回代码核对**：写进通过标准的每个字符串、数字、日志行都在代码里确认过真的会打出来。
4. **按执行者能力分工**：agent 只做命令行（git、构建、curl、读日志、写回执），**不碰桌面、不截图、不点界面**；界面由人看，给人一张能照着点的短清单。
5. **不重复已验证项、不凭空加前置条件**（设备台数、多余的 UI 验证）。用户原话：「你这些都验证过了，没必要再来一遍吧」「你为什么要五台设备？」

### B. 生成任务单 / 提示词

用 `references/prompt-template.md` 的骨架，**一次给出可整段复制的完整文本**，不让用户自己拼。必备段落：

- 任务一句话 + 边界（只取证 / 只打包 / 不改代码）
- 规矩（引用仓库文档，不复述；不碰无关项目；会打断人的动作先问；拿不准就停）
- **第 0 步核对版本**：`git pull` → `git log --oneline -1` 必须是 `<hash>` 或更新 → 工作区干净，不对就停
- 分组步骤（编号 1、2… 或轮次 A/B），每步写清：命令、要收集的证据、失败时怎么办（重试上限）
- 人工清单（需要人看的，单独一节）
- 回执要求（写到哪、什么格式、提交什么）

仓库协议模式：写入 `当前任务.md`（旧任务归档到 `历史任务/`）→ 提交推送 → 告诉用户「对 Windows 说：按联调任务执行」。
任务审批完、暂时没有新任务时，把 `当前任务.md` 改成空闲声明：「当前没有待执行的联调任务。不要重跑历史任务。」
粘贴模式：直接在回复里给出完整提示词代码块。

### C. 收回执：先核验新鲜度，再判结论

回执到了（git pull 到新文件，或用户粘贴），**按 `references/review-checklist.md` 逐项核对**，核心是：

1. **时间与版本**：回执日期是今天/本轮？被测 commit 是否 ≥ 本轮推送的 hash？产物修改时间是否晚于拉取时间？版本号是否等于本轮版本？任一不符 → 结论「不可测」，不往下判。用户原话：「你不看回执文件是什么时候的吗？今天几号？」
2. **逐项判定**：对照任务单编号，每项 ✅/❌/⏭；数字要具体值；判据看**设备侧独立证据**，不只信被测系统自己的返回。
3. **回执是带日期的证据**：引用时写「回执 N（日期、提交）显示…」，不外推成「至今没验证/一直不生效」；和用户真机体验对不上，先问场景。

### D. 审批与下一步

- 写审批：仓库协议模式在**同一回执文件末尾**追加 `## 审批`（通过 → 下一步 / 打回 → 原因 → 我要改什么），提交推送。
- 用大白话一次性汇报：**结论先行**（通过 / 部分通过 / 阻塞），再列失败项与原因判断。
- 有失败项 → 修代码 → 生成**复验提示词**：只含未过项和本轮改动影响到的项，已通过的不再跑。
- 跨多轮的问题本轮确认解决 → **主动调用 `postmortem` skill** 写独立归因，不等用户问。
- 新被回执证实的设备约束 → 当天补进行为回放测试或归因文档。

## 执行侧（Windows）

职责只有三件事：**拉代码 → 照单执行 → 写回执推回去**。

1. `git pull`（分支以任务单为准）。读协议 README 和当前任务单，两份读完再动手。任务单是空闲声明就回复「当前没有联调任务」并停下，**不重跑历史任务**。按第 0 步核对 commit，不对就停下回报。
2. 严格按编号顺序执行，每项「证据从哪拿」就是要收集的东西。
3. 回执格式**照抄**项目协议的骨架（没有就用 `references/receipt-template.md`）：表格一项一行；日志原样贴、不截断、不总结、不翻译；数字写具体值。
4. 只提交回执文件（`git add <回执路径>`，**禁止 `git add .`**），commit message 按项目约定，推送。
5. 一句话汇报：通过 / 部分通过 / 阻塞 + 回执文件名。然后停止。

**硬规则**

- 不改源码、不提交源码、不提交二进制和本机配置。测试或构建失败 → 写进回执然后停下，修是 Linux 侧的事。
- 例外：任务单**明确授权**的发版动作（合并 master、打 tag、发 Release、回填发版信息文档）可以做，但每一步先问人确认，原话抄进回执。
- 环境问题（缺依赖、路径）可以自己修，写进回执「偏离」。
- 不碰桌面：不点界面、不抢焦点、不截图；装包、重启应用、拔插数据线等会打断人的动作**先问一句**。
- 重试不超过任务单允许的次数；超过就标 ❌，记下现场，继续下一项。
- 拿不准不猜，写进「疑问」。写下自己的判断和反例（「同一轮单步却成功了」）比只贴报错有用。
- 写文件用编辑器或 `Set-Content -Encoding utf8` 整文件写入，不用 PowerShell 字符串拼接（反引号会被吃掉）。提示词和回执里的路径一律用正斜杠，反斜杠经过多层传参容易被吞。

## 通用约束

- 凭据（共享盘账号、API key）只从本机配置读取，不写进任务单、提示词、回执、仓库。
- 人要做的事写成能照着点的短清单，用户原话抄进回执；不要问人日志里就有的东西。
- 汇报用简体中文、大白话、结论先行。
