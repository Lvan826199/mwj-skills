# Windows 驱动与设备枚举

## libusb-win32 过滤驱动

投屏需要 libusb 直接访问设备，同时 Apple 自己的驱动（AMDS、usbmuxd）也要能用，所以用**过滤驱动**和 Apple 驱动共存，不替换 Apple 驱动。

### 只写父节点的 UpperFilters

- 写入位置：**Apple 复合设备父节点**的 `UpperFilters`，SetupAPI 属性码 `SPDRP_UPPERFILTERS = 0x11`。
- 曾经写成了 `0x12`（那是 `SPDRP_LOWERFILTERS`）。日志按变量名打印成 UpperFilters，回读验证又用了同一个错的常量，结果一直「自洽地通过」，最后整台电脑都读不到 iOS 设备。
- **绝不写 `MI_00` / `MI_01` 这类接口子节点**：libusb0 挂到 Apple 的接口节点上，会打断 Apple 的通信链路。
- **验收要用独立手段**：`reg query` 查看真实的键名和值，不能用写入时的同一个常量来自证。
- 已经中招的机器：先清掉错误的过滤器，恢复 Apple Mobile Device Support，再按上面的规则重装。

### 安装流程的坑

- 不要依赖外部的 `install-filter.exe`。它按带 REV 的硬件 ID 写入时，可能写不到真实的设备节点，还会顺带写接口子节点。改为自己调 SetupAPI：遍历在场的设备 → 比对硬件 ID → 写入 → 回读。
- 外部工具报「成功」，不等于事情真的做成了。凡是改系统状态的操作，都要自己把结果读回来验证。
- 写完注册表后**不要同步调用 `DIF_PROPERTYCHANGE`**。设备被 Apple 栈占用时，PnP 重枚举可能一直不返回，安装进程就卡死了。改为提示用户**拔插一次数据线**。
- 同一件事不要在 bat 脚本和程序里各写一套。路径判断这类逻辑放进程序里，bat 只负责提权和调用。
- 64 位 Windows 上，32 位的 libusb-win32 安装程序默认装到 `Program Files (x86)`（随包安装程序是 Inno Setup，静默参数见 open-issues.md）。不要写死安装路径，按注册表的卸载项或服务项去找。

## ctypes 调 Win32

返回句柄或指针的函数，**必须声明 `restype` / `argtypes`**（句柄用 `c_void_p`）。不声明的话，64 位句柄会被截断成 32 位，症状是「查不到设备」而不是报错，非常容易被误判成环境问题。

## 设备枚举与去重

- 同一台设备可能被枚举出两个节点（序列号相同）。按序列号去重：能打开 QuickTime 配置的节点优先，其次是能看到 usbmux 的。取不到序列号的节点不参与去重。
- 设备的序列号就是去掉连字符的 UDID，可以用它和 PnP 列表对上号。

## doctor 分层诊断

列不出设备时，按顺序逐层检查，每层直接给出下一步怎么做：

1. AMDS 服务（Apple Mobile Device Support）是否安装、是否在运行
2. Windows 是否看到了 Apple 的 USB 节点（看不到：数据线是充电线，或者没点「信任」）
3. usbmuxd 是否响应
4. 配对记录是否存在
5. 过滤驱动是否装上
6. 开发者模式是否开启

## 收尾时的蓝屏

- 收尾时**不要用 `set_configuration` 切回原配置**。
- 读线程没退出之前**不要释放接口**。
- 投屏期间设备只归投屏程序独占，其他工具（例如 go-ios、爱思助手）会失联，这是预期行为，要在文档里说明。
