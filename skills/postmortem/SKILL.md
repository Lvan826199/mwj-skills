# Postmortem：收工归因

用户原话：「这个卡顿问题解决的归因有写好吗？以后都要记得这个动作」「做总结写归因，以后不能出现类似的错误」。

**归因写在问题解决的那一轮，主动交付。** 逐轮的修复日志没人能连起来读，归因要单独成文，并且要写清「为什么」。

## 第 1 步：找项目已有的归因文件

```bash
ls -d doc*/*归因* doc*/*修复* doc*/*bug* doc*/*问题* 2>/dev/null
grep -nE "归因|bug.*(日志|记录)|postmortem" AGENTS.md CLAUDE.md 2>/dev/null | head -20
```

- 找到 → **沿用它的格式、分组、排序**（有的追加在分组末尾，有的新条目放最上面），先读最近 2～3 条照着写。
- 没找到 → 新建 `docs/问题归因.md`（表格档，见 `references/templates.md`），并在 AGENTS.md / CLAUDE.md 的文档同步表里登记一行。

## 第 2 步：选粒度

| 档 | 什么时候用 | 写在哪 |
|---|---|---|
| **表格行** | 单个 bug，一轮修好，根因清楚 | 归因表对应分组：`现象 \| 根因 \| 修法`（项目有「防复发」列就填） |
| **条目** | 项目用条目式日志，或需要记状态（待修 / 已修 / 明确不改） | 修复日志：现象 → 根因 → 修法 → 验证 → 状态 |
| **独立文档** | 跨多轮排查、多份回执、用户可感知的事故（数据丢失、卡顿、反复修不好），或用户明确要求 | `docs/归因/YYYY-MM-DD-<主题>.md`（项目已有别的位置就照旧），并在归因表/修复日志里加一行链接过去 |

拿不准选哪档 → 选高一档。独立文档写完，表格里仍要有一行索引。

## 第 3 步：写（硬规则）

模板见 `references/templates.md`。不论哪一档：

1. **现象用用户原话 / 回执原文**，不转述成自己的话。
2. **根因按证据分级**：`已确认`（代码可证 / 日志可证 / 复现过）、`高度可能`（机制成立、缺现场证据）、`未证实`（通道存在、未见发生）。每条附证据：代码位置、回执编号 + 日期 + 提交、日志原文。**不把「高度可能」写成「已确认」。**
3. **写「为什么」而不只是「改了什么」**：机制要讲到能让下一个人不看代码也懂。
4. **修法写具体改动**（文件、函数、关键常量），有修后数字就写修后数字（fps、耗时、行数）。
5. **验证**：怎么证明修好了——哪份回执、哪条测试、哪次真机。没真机验证的写「待真机验证」。
6. **教训要可迁移**：写成下次在别的项目也能用的一句话规则（「搬正在用的数据库，永远是复制 → 核对 → 切换 → 退役」），不写「下次注意」。
7. **涉及代码与探针清单**（独立文档档）：方便以后排障时搜。

## 第 4 步：同步

- **单轮问题**：归因和修复放在**同一个提交**里。
- **多轮问题**：修复早已分轮提交，归因在问题确认解决后**单独提交**，用 `docs(归因): <主题>`。

需要同步的内容：

- [ ] 归因文件（本 skill 的产出）
- [ ] `CHANGELOG.md` 的「未发布 / 修复」段补一句用户可见的描述（项目有 CHANGELOG 时）
- [ ] 计划 / 进度 / 问题跟踪文档里的对应条目改状态并链接归因
- [ ] 教训具有跨项目通用性 → 写一条 feedback 类记忆（项目记忆在仓库里就写进仓库，并更新索引）
- [ ] 教训能变成机器检查 → 提议补测试 / lint / 门禁（列出来，让用户选做不做）
- [ ] 教训属于下发或联调环节的 → 回写到项目的联调自检清单（如 MSCA `doc/联调/README.md` 的下发前自检）

提交信息：单独提交用 `docs(归因): <主题>`；和修复放在同一提交时用修复的 `fix(...)` 前缀，正文写一句「附归因」。

## 第 5 步：汇报

一段大白话：一句话结论 → 根因（标证据等级）→ 改了什么 → 教训 → 归因文件路径。不要把整篇归因贴进对话。
