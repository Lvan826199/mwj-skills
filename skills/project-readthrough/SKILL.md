# Project Readthrough：只读通读

用户原话：「先不改，你阅读下 msca 有没有其他隐藏的问题」「趁这个机会，你通读一下我们现在这个项目的代码」「先不要对项目有任何修改」。

**通读阶段仓库零改动。改什么由用户逐项选。**

## 第 0 步：确认范围与基线

1. 范围：整个仓库还是某几个模块；有没有重点（某个功能、某次事故、发版前把关）。用户没说清楚就用选项问一次。
2. 基线：
   ```bash
   git status --short; git log --oneline -1; git branch --show-current
   ```
   记下 commit。工作区不干净的，先问用户这些改动算不算在通读范围内。
3. 测试基线：只在**不会改动仓库**的前提下跑。用已有的 venv 直接跑，例如 `PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest -q -p no:cacheprovider`；没有 venv 就不跑，写进盲区；不用 `uv sync` 或 `npm install` 这类会改锁文件的命令。会触发热重载、写真实库的测试不跑。
4. 读项目规则：AGENTS.md、CLAUDE.md、记忆索引、近期的归因文档。标了「AI勿读」的文件不读。

## 第 1 步：建工作目录

**默认放在仓库外**，保证「零改动」可证：scratchpad，或本项目记忆桶下的 `readthrough-<YYYY-MM-DD>/`。
用户同意落进仓库时再挪到 `.planning/<YYYY-MM-DD>-readthrough/`（先确认 `.planning/` 是否在 .gitignore 里，不在就把它当作通读产出单独提交）。用 planning-with-files 时三个文件也放在这里，不覆盖根目录已有的规划文件。

- `task_plan.md`：范围、分工、阶段、决策
- `findings.md`：发现，结构见 `references/findings-template.md`
- `progress.md`：进度；收尾时写一行「仓库零改动」，附 `git status` 的输出

## 第 2 步：分工通读

- **核心层自己读完**：改动最集中、风险最高的模块。这里不能交给别人。
- **其余分给只读子代理**：前端、文档、测试、脚本各一个。小项目不用拆。
  - 用 Agent（Explore 或 general-purpose）或 `delegate-to-cli`，给每个子代理一张检查点清单，要求带文件名和行号作为证据。
  - **回收后主线必须抽查**：强结论逐条打开原文核对，核过的标 ✔。没核过的不能升为「已证实」。
- 重点看这些地方，大多数隐藏 bug 都在这里：
  - 接缝：单元测试全绿，但模块之间的对接从没测过
  - 同一个功能有两条调用路径，只验了一条
  - 默认值、分支条件改过之后，没带参数的命令实际走到哪条路径
  - 超时、重试常量和回执里的实测值对不上
  - 文档或注释说的和代码做的不一致
  - 运行时生成的文件没有被 .gitignore 覆盖
  - 回执打了 ✅，但其实是假阳性（只看了被测系统自己的返回）

## 第 3 步：证实

- 疑点尽量复现：复现脚本写在 **scratchpad 或 `/tmp`**，不写进仓库。脚本贴进 findings，附上运行输出。
- 引用回执或历史结论时，带上日期和提交号，再对照当前代码看还成不成立。**不要外推成「从没生效过」「一直有问题」**。
- 证据分四档，每条问题都要标：

| 档 | 含义 |
|---|---|
| **已证实** | 有脚本或命令复现，或代码逻辑可以直接推出；附行号 |
| **疑似 ⚠** | 机制成立，但没复现、缺现场证据 |
| **需真机** | 代码层面确认有问题，后果要真机或真实环境才能知道 |
| **卫生** | 文档与代码不一致、死代码、gitignore、命名，不影响行为 |

## 第 4 步：汇报，让用户选

findings 写完后，在对话里用大白话汇报（不要贴整份 findings）：

1. 一句话结论：整体健康度，最该先修的是哪几条。
2. 编号问题清单（R01、R02…），每条一行：严重度（P0–P3）、证据档、一句话现象、修复方向、修的风险。
3. **覆盖范围与盲区**：哪些部分没读或只是粗读，说清楚。
4. 用 AskUserQuestion 让用户选要修的项（多选，推荐项放前面）。涉及驱动安装、改写历史、强推、动已发版协议的，单独列出风险。

然后**停下等用户选**，不要自己开始修。

## 第 5 步：修复（用户选定后）

- 在通读工作目录追加一节「修复批次」（或新建 `<日期>-readthrough-fix/`）。**只修清单里选中的项**，顺手发现的新问题另外记下来。
- 每一项先写复现测试，再改代码；一个批次修完，跑一遍测试。
- 回填到 findings：每一项写明处理结果——
  - 已修：提交号、对应的测试
  - 用户决定不修：写清原因，标注「别推翻」
  - 故意没动：写清理由和风险
- 修复完成后调用 `postmortem`：单个 bug 各补一行归因，跨多处的系统性问题写一篇独立归因。
- 写一条记忆指针，指向这次通读的笔记位置，并写明「接手开发任务前先读」。

## 硬规则

- 通读阶段：不改代码、不改锁文件、不提交、不起会写真实库的服务；收尾时用 `git status` 证明仓库零改动。
- 子代理的结论没经过抽查，不算已证实。
- 报告里必须有「覆盖范围与盲区」一节。
- 不擅自开始修；用户选什么就修什么。
