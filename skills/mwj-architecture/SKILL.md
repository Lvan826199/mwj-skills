# MWJ Architecture：架构模式与守护

模式详情见 `references/patterns.md`，依赖方向测试模板见 `references/test_architecture_template.py`。

## 场景一：新项目选型

| 需求特征 | 选择 |
|---|---|
| 多用户、权限、数据库、后台异步任务 | **A** FastAPI 分层平台 |
| 领域规则复杂、外部依赖多、要长期防止腐化 | **B** 六边形架构 |
| 设备或硬件能力要给人用，也要给多语言宿主调用 | **C** CLI + sidecar |
| 执行引擎和管理平台要分开演进 | **C 变体**：引擎 CLI + 平台 |
| 离线桌面应用，同时要支持 Web 部署 | **D** Electron + Python 后端（可以内嵌 C） |
| 单用户本地数据，桌面和手机共用 | **E** pywebview + Android WebView |
| CPU/GPU 重计算、需要限流和可观测性 | **F** 推理引擎服务 |

做法：

1. 用一张选项表把推荐方案和理由给用户，**由用户拍板**（架构属于影响结果的关键决策）。
2. 定下来以后，按 patterns.md 里对应的骨架建目录；脚手架交给 mwj-project-init。
3. 把这个模式的「不可违反的规则」写进项目 AGENTS.md 的「架构」一节，并补上项目自己的不变量和改动联动表。
4. 有分层的项目（A、B、E、F），当天就把依赖方向测试接上（见场景三）。

## 场景二：改代码前，判断该放在哪、有没有越层

1. 先认出项目属于哪种模式：看目录骨架和 AGENTS.md 里「架构」一节。都对不上的，按项目自己的结构来，**不要强行套用**。
2. 读 patterns.md 里对应的一节，重点看「依赖规则」和「不可违反的规则」。
3. 对照这次改动检查：
   - 新代码放在哪一层？它 import 了哪些层？
   - 有没有新造出第二个定义点（同一个口径定义了两次）？
   - 有没有改到对外契约（协议、错误码、API 字段）？只能新增。
   - 有没有碰到改动联动表里的 X，却漏了对应的 Y？
4. 拿不准的，写成选项问用户，不要自己挑一个省事的放法。

## 场景三：补架构测试

1. 把 `references/test_architecture_template.py` 复制到 `tests/test_architecture.py`。
2. 按项目的分层改 `PACKAGE_ROOT` 和 `FORBIDDEN`（禁止列表里也可以写三方库，例如 core 不许 import webview）。
3. 先跑一遍。已有的违规**不要顺手修**：写进 `ALLOWED`，每条附一句原因，列给用户决定什么时候修。豁免**只许减不许增**，修好后由测试提醒删掉。
4. 进门禁：`scripts/check.sh` 或 CI 里跑 `-m unit` 时要包含这个测试。

模板做了这些处理：
- 用 AST 静态扫描，不用 `sys.modules`，避免把传递依赖也算进来造成误报。
- 跳过 `TYPE_CHECKING` 块。
- 展开相对导入和 `from 包 import 子模块`。
- 能扫到函数里、try 里的 import。

## 跨模式原则（每次设计和审查都对照）

1. 对外契约只增不改，带版本号。
2. 单一事实源：同一个口径只定义一次。
3. 确定性的事交给代码，语义判断才交给模型。
4. 错误要结构化：稳定 code + 人话 message + 建议。
5. 用测试守规则：违规基线只许缩，豁免必须写原因。
6. 进程生命周期要闭环：每条流都有出口；先优雅停止再结束进程；只清理自己的进程。
7. 数据不绑定机器：库里只存相对路径；正在使用的库不放进同步目录；迁移只补不覆盖。
8. 装配点唯一，测试替身也从装配点注入。
